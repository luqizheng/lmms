## 2. 已发现的发布阻断项

### P0 — 公网 SDK Workflow 会错误读取内网目标

文件：`.github/workflows/public-release.yml`

Workflow 当前：
- Rust 注入 `CARGO_REGISTRIES_CRATES_IO_TOKEN`，但执行 `coder release sdk rust`。
- npm 配置 `setup-node registry-url=https://registry.npmjs.org/`，但执行 `coder release sdk npm`。
- Docker 命令显式传入 `--registry docker.io --repo "$DOCKER_USER_NAME"`。

文件：`packages/cli/commands/release.js`

- Rust 发布目标直接来自 `readReleaseConfig().sdk.rustRegistry`。
- npm 发布目标直接来自 `readReleaseConfig().sdk.npmRegistry`。
- 当前 CLI 的 SDK 命令没有 Rust/npm Registry override 参数。

文件：`release.toml`

- `rust_registry = "kellnr"`
- `npm_registry = "http://192.168.2.12:14873/" `

文件：`packages/cli/lib/sdk-publish.js`

- Rust 的 `publishRust()` 强制要求 registry 参数，并将其传给 `cargo publish --registry`。
- npm 的 `publishNpm()` 将 registry 参数显式传给 pnpm publish。
- 因此仅设置 npm 的 setup-node registry-url，或仅注入 crates.io token，都不能覆盖 CLI 的私有 Registry 参数。

**结论：当前 Workflow 不能安全执行 Rust/npm 公网发布。** 必须先增加显式且可测试的公网目标 override（crates.io 需使用 Cargo 默认 registry 语义，不能错误地把 `crates-io` 当作私有 registry alias），再让 Workflow 对 dry-run 与 publish 使用同一显式目标。

### P1 — Docker Hub namespace 尚未完成核验

Workflow 使用 `DOCKER_USER_NAME` 作为 Docker Hub namespace，并将镜像写入该 namespace。当前没有通过 Docker Hub API 逐项确认该 namespace 下 7 个目标 repository 的归属、现有 tag 和冲突情况。不得仅凭 Secret 名称推断 namespace。

### P1 — 执行环境与凭据能力限制

本次可用 GitHub 接口支持仓库读取和普通文件写入，但没有可用的 Actions workflow_dispatch 触发操作，也没有读取 GitHub Environment Secrets 值或验证其存在性的能力。因此不能在此会话中安全地启动现有 GitHub Actions 发布任务。Secret 应由 GitHub Actions 在运行时注入，不应复制到对话或仓库。
