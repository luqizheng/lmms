# Phase 4.0 — 数据表命名规范统一

> Status: Draft → Review
> Date: 2026-06-26
> Scope: 前置任务，Phase 4 事件总线开工前必须合并
> Successor: `2026-06-26-phase4-event-bus-design.md`

---

## 1. 问题陈述

当前所有 Rust 服务（iam / audit / token / notification / config / file / prue_backend）连接同一个 MySQL 实例的同一个 database `superpowers`，但**没有任何表名隔离约定**，已经出现实际冲突：

| 服务 | 表名 | 状态 |
|---|---|---|
| iam-service | `users` / `roles` / `permissions` / `menus` / `org_units` / `user_roles` / `role_permissions` / `user_org_units` / `refresh_tokens` / `login_logs` | V001 用 `IF NOT EXISTS` |
| audit-service | `operation_logs` / `login_logs` / `api_access_logs` | V001 用 `CREATE TABLE`（无 IF NOT EXISTS） |
| token-service | `oauth_clients` / `auth_codes` / `revoked_jtis` / `refresh_markers` | — |

**两个 `login_logs` 已经在同库里撞名**。谁先跑迁移谁占位，后跑者迁移直接报错或被静默跳过 —— 这是个潜伏的 P0 数据正确性 bug。

Phase 4 要新增 outbox / audit_events 等更多表，再不立约定坑会越挖越大。本 Phase 0.0 在 Phase 4 主任务开工前一次性把规范定下来 + 把存量表迁过去。

---

## 2. 范围

### In Scope
- 制定项目级表命名前缀规范，写入 `contracts/db-conventions.md` 和 `agents.md`
- 把现有所有业务表通过 `RENAME TABLE` 迁移到带前缀的新名字
- 把所有 sqlx 查询里的表名一次性改过来
- 加 CI gate：扫描所有 `migrations/*/V*.sql` 与代码中的 SQL，禁止出现无前缀的 `CREATE TABLE` / `FROM <无前缀名>` 模式

### Out of Scope
- 不拆 database / schema（保留单库 `superpowers`，未来 Phase 7 K3s 化时再考虑物理隔离）
- 不改字段名 / 索引 / 外键
- 不动 SQLite 分支（prue_backend）—— SQLite 单实例无共库问题；但其表名也按规范加前缀以保持代码一致性

## 3. 前缀映射

| 服务（crate） | 前缀 | error-codes.yaml 对应缩写 | OpenAPI tag 对应 |
|---|---|---|---|
| iam-service | `iam_` | IAM | iam |
| audit-service | `audit_` | AUD | audit |
| token-service | `token_` | —（暂用 SYS） | token |
| notification-service | `ntf_` | NTF | notification |
| config-service | `cfg_` | CFG | config |
| file-service | `file_` | FILE | file |
| prue_backend | `prue_` | —（不在错误码体系内） | prue |

> error-codes 缩写与表前缀**故意不完全一致**：错误码追求短（3 字母），表名追求可读（完整或常用缩写）。两者各自有 schema 校验，无需强行对齐。

## 4. 重命名清单

### 4.1 iam-service（10 张表）

```sql
RENAME TABLE
    users             TO iam_users,
    roles             TO iam_roles,
    permissions       TO iam_permissions,
    menus             TO iam_menus,
    org_units         TO iam_org_units,
    user_roles        TO iam_user_roles,
    role_permissions  TO iam_role_permissions,
    user_org_units    TO iam_user_org_units,
    refresh_tokens    TO iam_refresh_tokens,
    login_logs        TO iam_login_logs;
```

### 4.2 audit-service（3 张表）

```sql
RENAME TABLE
    operation_logs    TO audit_operation_logs,
    login_logs        TO audit_login_logs,   -- 与 iam_login_logs 解决撞名
    api_access_logs   TO audit_api_access_logs;
```

> 注：audit 的 `login_logs` 历史上和 iam 的 `login_logs` 同库撞名 —— 实际只有一张物理表存在。**迁移前必须排查**：到底当前生产 / dev 环境里这张表是 iam 写的还是 audit 写的？由谁的代码在读？4.0 实施计划里这是第一步。

### 4.3 token-service（4 张表）

```sql
RENAME TABLE
    oauth_clients     TO token_oauth_clients,
    auth_codes        TO token_auth_codes,
    revoked_jtis      TO token_revoked_jtis,
    refresh_markers   TO token_refresh_markers;
```

### 4.4 其他服务

- **notification-service / config-service / file-service / prue_backend**：实施时 grep 实际表清单（spec 撰写时未逐一展开，避免漏。计划阶段 step 1 就是「扫库出权威清单」）

## 5. 代码同步改动

### 5.1 sqlx 查询

每个服务的 `src/` 下所有 SQL 字符串（`sqlx::query!` / `sqlx::query_as!` / 拼接的 SQL）里的表名一次性替换。预计每服务 < 100 处。grep 模式：

```bash
rg "\b(FROM|JOIN|INTO|UPDATE|TABLE)\s+(users|roles|permissions|menus|org_units|...)\b" services/iam-service/
```

### 5.2 fixture / seed / 测试

- `tests/e2e/` 里若有直接 SQL 操作的 setup（teardown / globalSetup），同步改
- 各服务 `tests/` 集成测试里的 SQL 同步改
- `migrations/mysql/V001__init.sql` **不动**（V001 已上线就是已上线）；用新的 `V00X__rename_tables.sql` 做迁移

### 5.3 文档

- `services/<svc>/README.md` 提到表名的地方
- `docs/ai-context.md` 服务地图节追加一句指向 db-conventions
- `services/<svc>/AGENTS.md` 加一句「新增表必须以 `<prefix>_` 起头」

## 6. 新规范文档

新建 `contracts/db-conventions.md`，节选大纲：

1. 单库多服务现状说明
2. 表前缀映射表（4.0 节内容）
3. 命名规则：
   - 表名：`<prefix>_<resource_plural_snake_case>`，例 `iam_users` / `audit_login_logs`
   - 索引名：`idx_<table>_<cols>` / `uk_<table>_<cols>`
   - 外键名：`fk_<table>_<col>`
4. 例外：
   - SQLite 单服务模式（prue_backend）仍加前缀，保持代码统一
   - 第三方组件自带表（sqlx migration metadata 等）不强制
5. 检查方式：CI gate `scripts/check-db-naming.js`

---

## 7. CI gate

新增 `scripts/check-db-naming.js`：

- 扫描 `services/*/migrations/**/*.sql`：
  - 所有 `CREATE TABLE [IF NOT EXISTS] <name>` 中 `<name>` 必须以该服务前缀起头
  - 所有 `ALTER TABLE <name>` 同上
- 扫描 `services/*/src/**/*.rs`：
  - 所有 `sqlx::query*` 宏 / 字符串里出现的 `FROM <name>` / `JOIN <name>` / `INTO <name>` / `UPDATE <name>` 必须以该服务前缀起头
  - 例外白名单：跨服务只读查询场景（Phase 4 之后应该没有，写报错）

加入 `.github/workflows/` 或 `.gitlab-ci.yml` 的 test stage。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 漏改 sqlx 查询导致运行时报错 | CI gate `check-db-naming.js` 阻断；本地 `cargo test` + e2e 兜底 |
| `RENAME TABLE` 在 sqlx-cli flyway-style 迁移工具下的执行顺序 | iam V001 用了 `IF NOT EXISTS` —— 即便迁移已跑过，新迁移 `RENAME TABLE users TO iam_users` 在 V001 之后顺序执行，安全 |
| audit / iam 的 `login_logs` 撞名 —— 现实里只有一张表 | 实施 step 1：先在 dev/test 库 `SHOW CREATE TABLE login_logs` 看 schema，确定它属于哪个服务；按归属迁过去；另一服务的 V001 等效 INSERT/查询在新表名上重建（这里可能需要把 audit 的 login_logs 用 `INSERT IGNORE` 重建一份从 iam_login_logs 拉过来 —— 这是个边界 case，需在实施计划里展开） |
| 生产环境数据 | 暂未上生产，dev/test 环境可破坏性迁移；后续生产上线时把 V00X 作为新库 schema 一部分跑即可 |
| 迁移期间多副本部署 | 与 Phase 4 一样，要求一次性切换（开发/测试环境本来就 reset schema 频繁） |

## 10. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 隔离方式 | 表名加前缀（不拆 database） | 用户选型；改动小，未来拆库时 `<prefix>_*` 全部移到新库即可，前缀本身就是分库参考 |
| 迁移方式 | 一次性 RENAME TABLE | 用户选型；dev/test 环境本就破坏性迭代，不留双表负担 |
| 前缀映射 | iam_/audit_/token_/ntf_/cfg_/file_/prue_ | 用户选型；与错误码缩写解耦，各自服务语义 |
| SQLite | 仍加前缀 | 保持代码统一，避免 mysql/sqlite 分支差异 |
| 时序 | Phase 4 主任务前置 | 避免在错地基上盖楼 |
