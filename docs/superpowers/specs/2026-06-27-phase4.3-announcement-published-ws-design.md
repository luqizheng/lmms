## 1. 概述与动机

### 问题

`WsHub`（`services/notification-service/src/ws_hub.rs`）是**进程内**的：每个用户的 WS 连接订阅
本副本的 tokio broadcast channel。多副本部署时用户 WS 落在副本 A、发布动作可能发生在副本 B，
WS 推送到不了。此外当前发布路径是残废的：

- REST `publish`（`rest.rs:94`）只 `set_status(Published)`，不插 delivery、不推 WS。
- scheduler `publish_one`（`scheduler.rs:30`）解析 recipient scope 后丢弃（空 user 集），同样什么都不做。
- 因为不插 `ntf_announcement_deliveries`，`list_for_user`（JOIN deliveries）查不到已发布公告。

### 方案

发布时把目标用户解析出来（本期仅 **user-scope**），在同一事务里：插 delivery + 翻 Published +
经 outbox enqueue `notification.announcement.published`（携带 user_id 列表）。
`ntf-outbox-publisher` 二进制把事件发到 RabbitMQ `events` topic exchange。
每个副本各自声明一个 **exclusive/auto-delete 队列**消费该事件，对本地连接的、命中 user_ids 的
用户推 `WsOut::New`。notification-service 首次成为事件**生产者**。

### 范围

仅 user-scope 的事件驱动 WS 扇出 + delivery 持久化。

### 不在本期范围（follow-up，文档记录）

- **role/dept 接收人解析**：`recipient_resolver::expand_local` 的数据源、iam 成员查询端点缺失，
  本期仅处理 `scope_type='user'`，role/dept scope 记 warn 并跳过。
- **4.1 welcome 路径多副本化**：`ensure_welcome_for_user` 仍进程内直推（不同事件、单用户）。
- **推送 metrics**（`ws_announcement_push_total`）。
- 推送幂等去重（见 §4.3，有意不做）。
- **大规模扇出批量 delivery INSERT**【评审 8A】：当前逐条 `INSERT IGNORE`（复用 `db.rs:insert_deliveries` 模式），user-scope 规模小不成问题；role/dept 大规模扇出落地后再批量化（TODO 4.3-fu1，依赖 role/dept 解析 TODO 4.3-fu2）。

## 2. 事件契约 + RabbitMQ 拓扑

### 2.1 契约（`contracts/events.yaml` 新增）

```yaml
  notification.announcement.published:
    schema_version: 1
    description: "公告已发布（触发 WS 推送扇出）"
    payload:
      announcement_id: { type: int,    required: true }
      title:           { type: string, required: true }
      pinned:          { type: bool,   required: true }
      popover:         { type: bool,   required: true }
      user_ids:        { type: json,   required: true }   # Vec<String>，本次推送目标
```

- codegen 生成 `NotificationAnnouncementPublished` struct + `impl Event`
  (`event_type()=="notification.announcement.published"`, `schema_version()==1`) +
  routing-key 常量 `NOTIFICATION_ANNOUNCEMENT_PUBLISHED`。
- `user_ids` 用 `json` 类型 → codegen rustType 映射为 `serde_json::Value`（现有约定）。
  生产端塞入 `serde_json::json!(Vec<String>)`，消费端 `serde_json::from_value::<Vec<String>>`。
- codegen 仍会把它加入命名不当的 `IamEventEnum`，无害——consumer 直接用
  `Envelope<NotificationAnnouncementPublished>`，不碰该 enum。
- 跑 `node scripts/contracts-gen.js` 生成，`--check` 须 in-sync。

### 2.2 拓扑

- Exchange：复用现有 `events` topic exchange。
- 队列：**每副本运行时声明** server-named 队列，`exclusive=true`、`auto_delete=true`、
  `durable=false`、无 DLX，绑定 `notification.announcement.published`。副本下线自动清理。
- **声明时机【评审 2A】**：在 consumer 任务**启动时**即声明 + 绑定队列（非首次消费时懒加载），
  把竞态窗口从「队列未绑定」缩到「副本进程尚未启动」。一个**正在运行**的副本绝不会因懒绑定漏消息；
  进程启动前发布的事件由 §2.3 的 reload 兜底覆盖。
- 因 per-replica 动态创建，**不写进 `definitions.json`**（definitions 只放静态共享队列）。
- 生产副本自己也消费自己那份 copy，无特殊处理。

### 2.3 权衡（写明）

exclusive 队列非持久：发布瞬间若某副本/用户 WS 不在线，那条 live 推送对它丢失——可接受，
因为用户重连后走 `list_for_user`（依赖本期补的 delivery 行）拿到公告。outbox 保证事件至少
投递到「当时在线、已声明队列的副本」；live WS 本就是 best-effort。

## 3. 生产端：outbox 表 + 共享发布例程

### 3.1 新表 `ntf_outbox_events`

迁移文件 `services/notification-service/migrations/2026_06_27_outbox.sql`，**逐列等于** iam
`iam_outbox_events`（仅改前缀与索引名）【评审 4A】。列名/类型必须与 `common_event::MySqlOutboxRepo`
写死的 SQL 对齐：`event_id / event_type / routing_key / envelope_json / created_at / published_at`
（一旦不一致是运行时 SQL 错误，非编译错误）。完整 DDL 内联于 plan Task 2。按 notification 现有
`ensure_schema` 机制（`db.rs` 顶部 `include_str!` + 在 `ensure_schema` 内追加该迁移的
split-execute 循环）。表名走 `ntf_` 前缀（CI 网关 `check-db-naming.js`）。

### 3.2 共享发布例程 `Db::publish_announcement`

`async fn publish_announcement(&self, ann_id: u64) -> AppResult<Vec<String>>`，
REST 与 scheduler 都走它，全程一个事务。**实现需在 `publish_announcement` 上方加 ASCII 事务管线
图注**（5 步 + 两调用方 + 事件去向）【评审 5A】：

```
tx = self.pool.begin()
1) SELECT title,status,pinned,popover ... FOR UPDATE   ← 行锁【评审 3A】
   若行不存在 → commit + Ok(vec![])
   若 status ∈ {published, revoked} → commit + Ok(vec![])（幂等，不重复 enqueue）
2) 解析 user-scope 接收人：
   SELECT scope_type, scope_id FROM ntf_announcement_recipients WHERE announcement_id=?
   过滤 scope_type='user' → user_ids: Vec<String>
   （存在 role/dept scope 行时 warn! 记录并跳过——follow-up 4.3-fu2）
3) for uid in &user_ids:
     INSERT IGNORE ntf_announcement_deliveries (announcement_id, user_id, delivered_at) VALUES (?,?,NOW())
4) UPDATE ntf_announcements SET status='published' WHERE id=?
5) envelope = Envelope::new("notification-service", NotificationAnnouncementPublished {
        announcement_id: ann_id, title, pinned, popover,
        user_ids: serde_json::json!(user_ids) })
   MySqlOutboxRepo::with_table(pool.clone(), "ntf_outbox_events").enqueue(&mut tx, &envelope)?
tx.commit()
Ok(user_ids)
```

要点：

- **并发正确性【评审 3A】**：第 1 步 `SELECT ... FOR UPDATE` 锁公告行 + 状态守卫（仅未发布才继续）。
  防 scheduler tick 与管理员手点 publish 并发时都读到 `scheduled`、都继续 → 重复 enqueue + 重复扇出。
- **原子性**：delivery + status + outbox 同事务。事件不丢。
- **REST `publish`**（`rest.rs:94`）改为调用 `publish_announcement(id)`，删除裸 `set_status`。
- **scheduler `publish_one`**（`scheduler.rs:30`）改为调用 `publish_announcement(id)`，删除其当前
  丢弃 scope 的残废逻辑与直接 `hub.publish`。
- **不再本地直推**：`publish_announcement` **不**调用 `hub.publish`。统一由 consumer 推送
  （生产副本消费自己的队列副本再推，与其它副本一视同仁），避免「直推 + 消费再推」双推。
- `MySqlOutboxRepo::with_table`：4.2 已确认 repo 支持 `with_table`，表名做注入校验。
- `set_status` 若仍被 `revoke` 路径使用则保留；仅 publish 路径改走新例程。

## 4. 消费端：每副本 exclusive 队列 + WS 推送

### 4.1 common-event 库扩展

现有 `RabbitMqConsumer::subscribe`（`libs/common-event/src/consumer.rs`）写死 durable queue +
`x-dead-letter-exchange` + 固定 consumer tag `"audit-service"`，不适合 per-replica ephemeral 队列。

**重构【评审 1B】**：抽出私有 `subscribe_inner(queue, bindings, opts: SubscribeOptions, handler)`，
`subscribe` 与 `subscribe_ephemeral` 都成为它的薄封装，消除两份 ~40 行 channel/exchange/bind/spawn
样板。`SubscribeOptions { durable, exclusive, auto_delete, with_dlx, consumer_tag }`：

- `subscribe`（现有语义）：durable=true、with_dlx=true、tag 由 `queue` + uuid 派生（**取代写死的 `"audit-service"`**）。
- `subscribe_ephemeral`（新）：server-named（空队列名，用 broker 返回的实际名绑定）、exclusive=true、
  auto_delete=true、durable=false、with_dlx=false、随机 tag。

加单测确认队列声明选项正确，并加一个 fanout 集成测试：两个 ephemeral 订阅者订阅同一 binding，
发一条消息，断言**两者都收到**（验证 fanout-to-all 而非竞争消费）。

### 4.2 新 consumer 模块

`services/notification-service/src/consumer/announcement_events.rs` + 在 `consumer/mod.rs`
注册第二个订阅（与现有 `notification.iam-events` 并存）。**实现需在该模块顶部加扇出 ASCII 图注**
（events exchange → per-replica copy → 本副本 hub.publish）【评审 5A】：

```
run(hub, event_bus_url):  5s reconnect loop（套现有 consumer/mod.rs run/try_subscribe 模式）
try_subscribe:
    consumer = RabbitMqConsumer::new(url)
    consumer.subscribe_ephemeral::<NotificationAnnouncementPublished, _, _>(
        &["notification.announcement.published"],
        move |env| async move { handle(&hub, &env).await })
handle(hub, env):
    let users: Vec<String> = serde_json::from_value(env.payload.user_ids.clone())
        .unwrap_or_default();
    for uid in users {
        hub.publish(uid, WsOut::New(serde_json::json!({
            "id": env.payload.announcement_id,
            "title": env.payload.title,
            "pinned": env.payload.pinned,
            "popover": env.payload.popover,
        }))).await;
    }
    Ok(())
```

### 4.3 幂等

无去重。重复投递就重推 `WsOut::New`；前端按 announcement id 去重，live WS best-effort
（与 4.2 risk consumer 同立场）。

### 4.4 接线

`main.rs` 在现有 iam consumer spawn 之外，再 spawn announcement consumer（传 `hub` clone +
event_bus_url），同 5s reconnect。

### 5.3 测试

- **单元**：`publish_announcement` user-scope 解析 helper（`filter_user_scope`：user 保留 / role+dept 计数跳过）；codegen 断言（Task 1）；outbox 迁移列断言（Task 2）。
- **集成（testcontainers MySQL）** —— 覆盖测试评审 4 个缺口：
  - **B 正常路径**：插带 user-scope recipients 的公告 → `publish_announcement` → 断言
    `ntf_outbox_events` 一行、`ntf_announcement_deliveries` 对应行、status=published。
  - **C 幂等守卫【评审 6A】**：对已 published 公告二次调用 `publish_announcement` → 返回空、
    `ntf_outbox_events` **不新增**行（验证 3A 行锁 + 状态守卫）。
  - **D role/dept 跳过【评审 7A】**：混合 scope（user+role+dept）→ 仅 user 进 user_ids + deliveries。
  - **E 空接收人【评审 7A】**：仅 role/dept scope（无 user）→ 仍翻 published、enqueue 一条空 user_ids 事件。
  - **I reload 兜底【评审 6A】**：publish 后**无任何 WS 连接**，`list_for_user` 仍返回该公告
    （验证 delivery 行是 best-effort 推送的持久兜底）。
- **集成（端到端扇出，testcontainers RabbitMQ）**：见 §4.1 fanout 测试（两 ephemeral 订阅者都收到）；
  announcement consumer handler 的 user_ids 解析 → hub.publish 由该测试或探针覆盖（与 §4.1 重叠时不重复）。
- **回归**：`contracts-gen --check`、`check-db-naming`、common-event + notification-service 全测试。

### 5.4 Live 冒烟（人工验收）

起两副本 notification-service，用户 A 连副本 1 的 WS，从副本 2 发布含 A 的 user-scope 公告 →
A 的 WS 收到 `new`；A 重连后 `list_for_user` 能看到该公告。

## 6. 成功标准

1. 发布（REST + scheduled）统一走 `publish_announcement`：同事务插 delivery + 翻 published + enqueue 事件。
2. `ntf-outbox-publisher` 将 `notification.announcement.published` 发到 events exchange。
3. 每副本各自 exclusive 队列消费，对本地连接的、命中 user_ids 的用户推 `WsOut::New`。
4. user-scope 接收人重连后经 `list_for_user` 仍能看到公告（delivery 已落库）。
5. role/dept 解析、4.1 welcome 多副本化、推送 metrics 明确列为 follow-up。
6. 全部测试 + 命名/契约门禁通过。
