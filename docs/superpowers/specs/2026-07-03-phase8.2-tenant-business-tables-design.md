# Phase 8.2 — 业务表 tenant_id 迁移

> 日期：2026-07-03
> 来源：`TODO.md` Phase 8.2「业务表 tenant_id 迁移（待 brainstorm）」。
> 前置：Phase 8.1 骨架已合并（`iam_tenants` + `iam_users.tenant_id` + `Principal.tenant_id` + `TenantScope` + `WithTenantScope` + JWT `tid` claim + `POST /iam/tenants` 注册 + `envelope.tenant_id` 接入）。
> 范围：iam / audit / ntf / cfg / file 五个服务的业务表加 `tenant_id` 列与索引，所有 tenant-owned 资源的 SELECT/INSERT/UPDATE/DELETE 改为 tenant-scoped，default tenant backfill，roles 改为租户内 + 注册流程复制模板，消费侧 `envelope.tenant_id` 落库。
>
> **不在本期范围**：gateway 跨租户访问检测、JWT 缺 `tid` 收紧 401、`scripts/check-tenant-scope.js` lint、platform-admin `cross_tenant` flag、e2e 跨租户黑名单 —— Phase 8.3。
>
> **已锁定的设计决策**（brainstorm 2026-07-03，所有问题取推荐方案）：
> - D1 单 spec 覆盖全部 5 个服务，实现按服务排序：iam → audit/ntf → cfg/file（共享同一 tenant 模型，避免跨 spec 漂移）
> - D2 permissions 全局 / roles 租户独有（沿用 8.1 决策；`iam_permissions`/`iam_menus` **不加** tenant_id）
> - D3 表覆盖范围 = 主表 + 审计日志 + `audit_events`；子/关联表靠 FK JOIN 推导（不加冗余列）；outbox / idempotency / templates 保持租户无感（envelope 已带 tenant_id）
> - D4 `prue_menu_configs` 全局，不加 tenant_id（与 iam_menus/permissions 全局对称）
> - D5 `tenant_id` 类型 `BIGINT UNSIGNED`，FK → `iam_tenants(id)`（仅 iam 表）；audit/ntf/cfg/file 用裸 `BIGINT UNSIGNED` + 索引（微服务不跨服务 FK）。默认 `NOT NULL DEFAULT 1`，**唯一例外** `audit_events` 为 `NULL`（consumer 容错缺失 tenant 的事件）
> - D6 执行策略：每服务各自一个迁移（`V004` iam / `V002` 其余），forward-only，dev 期 `DEFAULT 1` backfill，无遗留数据需小心迁移
> - D7 tenant_admin 取**全部全局权限**（非旁路、非子集），无需改 auth/gateway 旁路逻辑

---

## 1. 背景与问题

Phase 8.1 只让 `iam_users` 带 `tenant_id`，其余业务表仍全局共享。当前状态：

- `iam_roles` / `iam_org_units` / `ntf_announcements` / `cfg_namespaces` / `file_files` 等主表无 tenant 隔离，任意租户可见全部数据。
- **潜在 bug**：`notification-service/src/scheduler.rs:30` 执行 `SELECT tenant_id FROM ntf_announcements`，但该表**无 tenant_id 列**（Phase 4.4 写的前瞻代码，运行期会失败）—— 8.2 必须补上该列修复。
- **类型不一致**：`file_files.tenant_id` 是 `VARCHAR(64)`（早于 8.1 设计），与 8.1 的 `BIGINT UNSIGNED` FK 模型不符。
- **8.1 已知遗留**：`/iam/users` 列表/搜索（`user_svc.rs:215,226`）未注入 tenant 过滤，跨租户仍可见（`test-case/81-tenant-registration.md:58` 标注的已知限制）。
- **两处硬编码 `envelope.tenant_id`**：`perm_change.rs:39` 与 `auth_svc.rs:372` 仍 `.with_tenant_id("1")`，未取真实 tid。
- **audit 日志表无写入方**：`audit_operation_logs` / `audit_login_logs` / `audit_api_access_logs` 在 Rust 代码中只有读路径（`audit.rs` 全 SELECT），无 INSERT；`audit_events` 由 consumer 从 envelope 写入。
- **tenant_admin 权限缺口**：`tenant_admin` seed 角色（V003）无任何 `iam_role_permissions` 记录，且 auth/gateway 无 admin 旁路 —— 注册的 admin 用户权限为空。

## 2. 目标 / 非目标

### 目标

1. 五服务主表加 `tenant_id` 列 + 索引 + 唯一键重建（roles/org/namespaces 的 unique key 纳入 tenant_id）。
2. 所有 tenant-owned 资源的查询/写入改为 tenant-scoped（列表用 `WithTenantScope::and_tenant`，点查询 bind `Principal.tenant_id`）。
3. roles 改为租户内：注册流程同事务建 per-tenant `tenant_admin` 角色 + 绑定全部全局权限 + 赋给 admin；V004 把 seed 角色收归默认租户并补权限。
4. 消费侧注入：`audit_events` / `ntf_announcements`（welcome）从 `envelope.tenant_id` 解析落库；ntf scheduler 读取列修复。
5. 修复 8.1 遗留：`/iam/users` 列表 tenant 过滤、两处硬编码 `with_tenant_id("1")`。
6. `file_files.tenant_id` 类型对齐 `BIGINT UNSIGNED`。

### 非目标

- gateway 跨租户检测 / `tid` 缺失 401 / `check-tenant-scope.js` lint / platform-admin `cross_tenant` / e2e 跨租户黑名单 —— Phase 8.3。
- audit 日志表的写入方（audit-capture 机制）—— 本期仅加列 + 读侧过滤，写入侧待未来。
- tenant 计费 / quota / 生命周期管理 —— 产品形态明确后另开。
- 可配置角色模板集 —— YAGNI，当前只需 `tenant_admin` 一个角色。

## 3. 设计

### 3.1 跨服务 FK 原则

仅 `iam_*` 表 FK → `iam_tenants(id)`（iam 拥有租户实体）。`audit_*` / `ntf_*` / `cfg_*` / `file_*` 用裸 `BIGINT UNSIGNED NOT NULL DEFAULT 1` + 索引，**不跨服务 FK**（微服务边界）。每个迁移文件镜像其服务已有的方言目录（mysql + sqlite，若有）。

### 3.2 迁移表清单

#### iam-service `V004__tenant_business_tables.sql`（mysql + sqlite）

| 表 | 改动 |
|----|------|
| `iam_roles` | `ADD tenant_id BIGINT UNSIGNED NOT NULL DEFAULT 1` + FK→iam_tenants(id) + `idx(tenant_id)`；`DROP UNIQUE code` → `ADD UNIQUE uk_tenant_role_code(tenant_id, code)` |
| `iam_org_units` | `ADD tenant_id` + FK + idx；`DROP UNIQUE code` → `UNIQUE uk_tenant_org_code(tenant_id, code)` |
| `iam_login_logs` | `ADD tenant_id BIGINT UNSIGNED DEFAULT 1` + idx（user_id 可空，不强 FK） |
| seed `tenant_admin` | `UPDATE iam_roles SET tenant_id=1 WHERE code='tenant_admin'`（收归默认租户，去"全局共享"语义） |
| `iam_permissions` / `iam_menus` | **不动**（全局目录） |
| `iam_outbox_events(_archive)` / 关联表（`iam_user_roles` / `iam_role_permissions` / `iam_user_org_units`）/ `iam_refresh_tokens` | **不动**（FK 推导 / 租户无感） |

#### audit-service `V002__tenant_audit.sql`（mysql）

| 表 | 改动 |
|----|------|

#### notification-service `V002__tenant_ntf.sql`（mysql）

| 表 | 改动 |

| `cfg_config_items` / `cfg_config_versions` | **不动**（靠 namespace FK 推导） |

**无迁移**（全局，D4）。

**Backfill**：dev 期无遗留数据，`DEFAULT 1` 全覆盖，无需小心数据迁移。

### 3.3 SQL 改造策略

按查询形态分三模式：

**1. 列表/搜索（多行）** → `QueryBuilder` + `WithTenantScope::and_tenant(&scope)`：
- iam：`role_svc.rs:66 list`、`user_svc.rs:215,226 list/search`（**修复 8.1 限制**）、`org_svc.rs:99 tree`
- iam：`permission_svc.rs:90 list` → **不加** tenant 过滤（权限全局）
- cfg：namespace 列表
- ntf：公告列表
- file：文件列表（已带 tenant_id，仅对齐 bind 类型）
- audit：`audit.rs:85,144,189,218,250`（`String::from("… WHERE 1=1")` 动态拼接 → 追加 `AND tenant_id = ?`，值来自新增 `Principal`/`TenantScope` extractor）

**2. 点查询（get/update/delete by id）** → WHERE 追加 `AND tenant_id = ?`，值来自 `Principal.tenant_id`：
- `role_svc.rs:54,109,142,180`、`org_svc.rs:73,84,134,149,161,183`、`user_svc.rs:115,196,248,279`
- ntf 公告 get/update、cfg namespace get/update/delete、file get/delete
- 防止靠猜 id 跨租户访问（acme token 查 globex 角色 → 0 行 / 404）

**3. INSERT** → bind `tenant_id`（来自 `Principal`/`TenantScope`）：
- `role_svc.rs:38`、`org_svc.rs:62`、`user_svc.rs:81`（已 bind ✅）
- ntf 建公告、cfg 建 namespace、file 建（类型 `String`→`i64` 对齐）

**两处硬编码 `envelope.tenant_id` 修复**：
- `perm_change.rs:39` `.with_tenant_id("1")` → 从受影响 `user_ids` 推导：在**同一事务**内 `SELECT tenant_id FROM iam_users WHERE id = ?`（取首个受影响 user，触发角色已 tenant-scoped 故同事务 user 同租户），用其 tenant_id。`perm_change` 调用方（role_svc update/delete/assign、user_roles）无需改签名。
- `auth_svc.rs:372` `.with_tenant_id("1")`（登录事件）→ `.with_tenant_id(user.tenant_id.to_string())`（user 已在 `auth_svc.rs:43` 加载）

**Handler 接线**：操作租户级资源但尚未接收 `Principal` 的路由补 extractor（多数 iam 路由已为 `actor_id` 接收 Principal；ntf/cfg/file 路由在 plan 阶段审计）。`internal_users` 已租户隔离 ✅。

**Outbox publisher**：不变 —— 租户无感读所有未发布行；`envelope.tenant_id` 随 `envelope_json` 传播。

### 3.4 roles 模板复制 + 默认租户

**注册流程**（`TenantService::register`，同事务）：
1. INSERT `iam_tenants`（已有）
2. INSERT `iam_users` admin（已有，带 tenant_id）
3. **新增**：INSERT `iam_roles`（新 nanoid id，`tenant_id=新租户`，`code='tenant_admin'`，`data_scope='all'`）
4. **新增**：`INSERT INTO iam_role_permissions (new_role_id, permission_id) SELECT id FROM iam_permissions WHERE status='enabled' AND deleted_at IS NULL` —— tenant_admin 获全部全局权限
5. **新增**：INSERT `iam_user_roles`（admin_user_id, new_role_id）
6. INSERT outbox `iam.tenant.created`（已有，`with_tenant_id`）

**V004 对默认租户（id=1）的补偿**：
- `UPDATE iam_roles SET tenant_id=1 WHERE code='tenant_admin'`（seed 收归默认租户）
- `INSERT IGNORE INTO iam_role_permissions (role_id, permission_id) SELECT 'role-tenant-admin-seed', id FROM iam_permissions WHERE status='enabled' AND deleted_at IS NULL` —— **顺带修复默认租户 admin 权限缺口**

**取舍**：tenant_admin 取全部全局权限（非旁路、非子集），符合"租户管理员=租户内全权"，无需改 auth/gateway 旁路，权限仍走 JWT。不做可配置角色模板集（YAGNI）。跨租户/platform-admin 的 `cross_tenant` flag 属 Phase 8.3。

### 3.5 消费侧 tenant_id 注入 + audit 读侧

**数据流**：iam 生产事件时 `envelope.tenant_id` 已填（8.1 已做大部分；3.3 两处硬编码修复补齐）。下游从 envelope 解析落库。

**audit-service 消费侧**（`consumer.rs:66`）：
```sql
INSERT INTO audit_events (event_id, event_type, occurred_at, trace_id, producer, payload_json, tenant_id)
VALUES (?, ?, ?, ?, ?, ?, ?)
```
bind `env.tenant_id.as_ref().and_then(|s| s.parse::<i64>().ok())`（`Option`，缺失时 NULL）。

**notification-service 消费侧**（`announcement_service.rs:107`，iam.user.created → 欢迎公告）：
- INSERT `ntf_announcements` 增 `tenant_id` 列，bind `env.tenant_id.parse::<i64>()`（欢迎公告归新用户所在租户）
- 同事务 `ntf_announcement_recipients` 不变（挂 announcement 下，FK 推导）

**notification-service REST 建公告**（`rest.rs:105`）：
- 已传 `me.tenant_id`（Principal）→ INSERT bind tenant_id。仅 INSERT 语句加列，无需改逻辑。

**notification-service scheduler**（`scheduler.rs:29`）：
- **自动修复**：`SELECT tenant_id FROM ntf_announcements` 列已存在（V002 补上）。`publish_announcement(ann_id, iam_client, tenant_id)` 继续透传。无需改代码。

**audit-service 读侧**（`audit.rs:85,144,189,218,250`）：
- `String::from("… WHERE 1=1")` 动态拼接 → 追加 `AND tenant_id = ?`，值来自新增 `Principal`/`TenantScope` extractor

- `audit_operation_logs`/`audit_login_logs`/`audit_api_access_logs` **当前无写入方** —— 8.2 仅加列 + 读侧过滤；写入侧 tenant 捕获待未来 audit-capture，不在本期

**outbox publisher**（iam/ntf）：不变，租户无感。

## 6. 风险

- **唯一键重建**：`DROP UNIQUE … ADD UNIQUE` 在 MySQL 是 online DDL，dev 期无锁顾虑；但若存量数据违反新 unique（如两租户前已有重复 code）会失败 —— dev 期无数据，风险低。
- **`file_files` 类型对齐**：`VARCHAR(64)` → `BIGINT UNSIGNED`，存量非数字值会 `UPDATE … SET tenant_id='1'` 兜底；Rust 模型 `Option<String>` → `Option<i64>` 需同步改，否则编译失败。**SQLite 不支持 `ALTER TABLE MODIFY COLUMN`**，file V002 的 SQLite 版需用 recreate-table 模式（建新表 → 拷贝 → DROP 旧 → RENAME），dev 期无数据可简化。
- **audit 读侧 Principal**：audit 路由当前无 Principal，补 extractor 需确认其鉴权方式（service-jwt / admin token），避免 401 回归。
- **roles 模板复制事务膨胀**：全量全局权限 INSERT 在权限数大时单事务行数较多 —— 当前权限规模小，可接受；日后权限膨胀再优化为模板引用。
