# Phase 4.4: `iam.permission.changed` 事件 + 令牌失效（perm-epoch 双写）

> Spec ID: phase4.4-permission-changed
> Status: DONE
> Created: 2026-06-27
> Phase: 4.x 小迭代（每个子任务一个 spec）
> 前置: Phase 4 事件总线、4.2（outbox + iam.* → audit 自动落库）、4.3（subscribe_ephemeral / 生产者模式）

## 1. 概述与动机

### 问题

系统**没有服务端权限缓存**——用户权限在登录/刷新时烤进 JWT
（`digua_common::token::AccessTokenClaims.permissions`），gateway 与 `digua_authz::require_role` /
`digua_jwt_ctx::Principal` 都从 JWT 读权限，从不查缓存或 DB。因此管理员改了角色权限后，
**该角色下所有已登录用户的 JWT 仍是旧权限**，直到 token 自然过期或刷新。唯一既有失效手段是
gateway 的 jti 黑名单（`api-gateway/src/blacklist.rs`），单 token 粒度，无法按「用户」或
「角色」批量失效。TODO 所说「各服务缓存失效」无缓存可失效——4.4 真正要解决的是
**「改权限后已签发的 JWT 仍是旧权限」**。

### 方案：user-level perm-epoch 戳（双写）

引入 Redis 戳 `perm_epoch:{user_id} = <变更时刻 unix 秒>`。gateway 的 `auth_middleware` 在
校验 JWT + 查 blacklist 之后，多比对一次：**若 `token.iat < perm_epoch` → 401「permissions
changed, re-authenticate」**，用户下次请求被强制刷新拿到新权限。

epoch 戳由两条路径写入（互为补充）：

1. **iam 直写（即时主路径）**：iam 在权限变更写操作里，事务 commit 后直接
   `SET perm_epoch:{uid} now EX <ttl>`。gateway 立刻能读到 → 失效几乎零延迟。
2. **gateway consumer 兜底（强一致补偿）**：iam 同事务发 `iam.permission.changed`（outbox）；
   gateway 订阅该事件，消费时**幂等补写** `perm_epoch:{uid}`（`SET ... only-if-greater` 语义，
   见 §4.3）。若 iam 直写因 Redis 抖动失败，事件经 outbox 至少一次投递最终补上戳——
   关闭直写的 fail-open 窗口。

### 为什么是 perm-epoch 而非「token 落库 + 反查拉黑」

（架构评审结论，记录备查）access token 无状态、jti 不落库是本系统的根本设计；把每个签发 token
落库退回成有状态 session，是方向倒退。perm-epoch 在登录热路径**零额外写**，仅低频的「改权限」
才写；一条 `perm_epoch:{user_id}` 即可使该用户**所有**活跃 token 失效；`iat < epoch` 是全序
判据，**无并发签发漏网**（落库反查方案在「查询快照→拉黑」窗口内并发签发的 token 会漏）；
key TTL 自清，无需第二张表 + cleanup cron；真相源唯一（`iam_user_roles`），无快照漂移。

### 范围（触发点）

iam 三类写操作，均在事务内展开受影响 `user_ids`：
- `role_svc::assign_permissions`（role→permissions 改）
- role 禁用（`update` status→disabled）/ 删除（`delete`）
- permission 禁用（`update` status→disabled）/ 删除（`delete`）

### 不在本期范围（follow-up，文档记录）

- 新增 user→roles 写端点（`PUT /iam/users/:id/roles`）并接入失效（当前 user→role 仅在建用户时设）。
- 其它服务（非 gateway）若未来需响应权限变更。
- perm-epoch 比对的本地内存短缓存（降低 gateway Redis 读频）。

## 2. 事件契约 + perm_epoch 数据模型

### 2.1 事件契约（`contracts/events.yaml` 新增）

```yaml
  iam.permission.changed:
    schema_version: 1
    description: "用户有效权限变更（角色授权/角色禁删/权限禁删）→ 触发令牌失效"
    payload:
      user_ids: { type: json,   required: true }   # Vec<String>，受影响用户
      reason:   { type: string, required: true }   # role_permissions_changed | role_disabled | role_deleted | permission_disabled | permission_deleted
      actor_id: { type: string, required: false }  # 操作者 user_id（审计；当前路由未必能拿到，可空）
```

- codegen 生成 `IamPermissionChanged` struct + `impl Event`
  (`event_type()=="iam.permission.changed"`, `schema_version()==1`) + 常量
  `IAM_PERMISSION_CHANGED`。`user_ids` 为 `json`→`serde_json::Value`（约定同 4.3）。
- 路由键归 `iam.*` 域（生产者是 iam），自动命中 audit 现有 `iam.#` 绑定 → 审计落库零改动。
- 跑 `node scripts/contracts-gen.js` 生成，`--check` 须 in-sync。

### 2.2 perm_epoch 数据模型（Redis）

- Key：`{prefix}perm_epoch:{user_id}`（prefix 复用 gateway/iam 约定，见 §5.1）。Value：unix 秒。
- TTL = access token TTL（`config.jwt.access_token_ttl_minutes * 60`）。超过该时长，所有在变更
  时刻之前签发的 token 本就自然过期，戳再留无意义 → Redis 自清，避免无限累积。
- 写入语义：**取较大值**（`now` 通常单调，但 consumer 兜底可能晚于 iam 直写到达，必须不回退）。
  见 §4.3 的 set-if-greater 实现。

### 2.3 gateway 比对语义

`AccessTokenClaims` 已含 `iat: i64`（`libs/digua_common/src/token.rs:8`），无需改 claims。
非公开路由，在现有 blacklist 查询之后：

```
epoch = GET {prefix}perm_epoch:{claims.sub}
if let Some(e) = epoch { if claims.iat < e { return 401 "permissions changed, re-authenticate"; } }
// epoch miss（绝大多数用户）→ 放行
```

- blacklist `EXISTS` 与 perm_epoch `GET` 用一次 Redis pipeline 合并，减少往返。
- Redis 失败 → 与现有 blacklist 一致 `unwrap_or` **fail-open 放行**（保持现状语义；perm-epoch 是
  补充失效层，不是唯一闸门）。gateway consumer 兜底 + token 自然过期是后备。

## 3. iam 生产端

### 3.1 iam 接入 Redis

iam `AppState`（`state.rs`）当前只有 `MemoryCache`，无 Redis 连接。新增：
- `AppState` 加 `pub redis: Option<redis::aio::ConnectionManager>`（`Option`：Redis 不可用时
  iam 仍能启动，直写降级为 no-op，靠 gateway consumer 兜底）。
- `REDIS_URL` 配置 + 启动时连接（compose 已有 redis 容器）。
- `redis` crate 已是 iam 依赖（Cargo.toml:49）。

### 3.2 共享辅助例程

避免三个触发点重复，新增（service 层或 AppState 方法）：

```
// 在调用方的业务事务内调用：把事件写进 outbox（与业务写同事务）
async fn enqueue_permission_changed(tx, user_ids: &[String], reason: &str, actor_id: Option<&str>) -> Result<()>:
    if user_ids.is_empty() { return Ok(()) }            // 无人受影响 → 不 enqueue
    let env = Envelope::new("iam-service", IamPermissionChanged {
        user_ids: serde_json::json!(user_ids), reason: reason.into(), actor_id: actor_id.map(str)
    });
    MySqlOutboxRepo::new(db).enqueue(tx, &env)?

// 在事务 commit 之后调用：iam 直写 perm_epoch（best-effort，失败仅 warn）
async fn stamp_perm_epochs(redis, prefix, user_ids: &[String], ttl_sec: u64):
    let now = unix_now();
    for uid in user_ids {
        // set-if-greater（见 §4.3 同款 Lua/脚本或 SET + 比较），EX ttl_sec
        if let Err(e) = set_perm_epoch_if_greater(redis, prefix, uid, now, ttl_sec).await {
            warn!(error=%e, uid, "stamp perm_epoch failed (gateway consumer will backfill)");
        }
    }
```

要点：
- `enqueue` 在业务事务内 → DB 变更与事件原子。
- `stamp_perm_epochs` 在 commit 后 → epoch 早写只会让旧 token 早失效，不会漏失效（权限安全偏保守）。
- iam 直写失败不阻断请求（已 commit + 已 enqueue）；gateway consumer 兜底补写。

### 3.3 三个触发点的 user_ids 展开（均在各自写操作的事务内）

| 触发点 | 文件 | user_ids 展开 SQL | reason |
|--------|------|-------------------|--------|
| 角色授权 | `role_svc::assign_permissions` | `SELECT user_id FROM iam_user_roles WHERE role_id=?` | `role_permissions_changed` |
| 角色禁用 | `role_svc::update`（status 变 disabled 时）| 同上 | `role_disabled` |
| 角色删除 | `role_svc::delete` | 同上（在删 user_roles/软删前查）| `role_deleted` |
| 权限禁用 | `permission_svc::update`（status 变 disabled）| `SELECT DISTINCT ur.user_id FROM iam_user_roles ur JOIN iam_role_permissions rp ON ur.role_id=rp.role_id WHERE rp.permission_id=?` | `permission_disabled` |
| 权限删除 | `permission_svc::delete` | 同上（在删 role_permissions 前查）| `permission_deleted` |

### 3.4 顺带修复的现状脆弱点（改到即修）

- `role_svc::assign_permissions`（role_svc.rs:152）当前**非事务** DELETE + loop-INSERT 且吞错
  （`let _ =`）。改为真事务 + 错误传播，再在同事务 enqueue 事件、commit 后 stamp。
- `role_svc::delete` / `permission_svc::delete` 当前非事务，改为事务包住「软删 + 清关联表 +
  enqueue」，commit 后 stamp。
- `update` 仅在 status 由非 disabled → disabled 时才触发（避免改名等无关更新误失效）。

## 4. gateway 读侧 + consumer 兜底 + audit

### 4.1 gateway 读侧（perm_epoch 比对）

新增 `api-gateway/src/perm_epoch.rs`（与 `blacklist.rs` 同款轻量模块）：
```rust
pub async fn get_perm_epoch(conn, prefix, sub) -> Option<i64>   // GET {prefix}perm_epoch:{sub}
pub async fn set_perm_epoch_if_greater(conn, prefix, uid, ts, ttl_sec) -> Result<()>  // consumer 兜底用
```
`auth_middleware`（`middleware/mod.rs`）在 `is_blacklisted` 之后、`insert(claims)` 之前加比对
（§2.3 逻辑）；blacklist + perm_epoch 合并为一次 pipeline 往返；失败 fail-open。

### 4.2 audit 落库（零改动）

`iam.permission.changed` 命中 audit 现有 `audit.iam-events` 队列的 `iam.#` 绑定 → 自动落
`audit_events`（含 event_id 幂等）。无新增 binding/handler。

### 4.3 gateway consumer 兜底（强一致补偿）

gateway 新增 digua_common-event 依赖 + 一个 consumer：
- 队列：**per-replica ephemeral**（复用 4.3 的 `subscribe_ephemeral`）绑定 `iam.permission.changed`
  —— 每个 gateway 副本都要补写自己可见的 Redis（实际是同一 Redis，幂等 set-if-greater 无害），
  且不与 audit 的持久队列竞争。
- handle(env)：对 `env.payload.user_ids` 每个 uid，`set_perm_epoch_if_greater(uid, env.occurred_at, ttl)`。
  使用 `occurred_at`（事件发生时刻）而非消费时刻，保证与 iam 直写的时间基准一致。
- **set-if-greater 语义**（关键，§2.2）：iam 直写与 consumer 兜底可能乱序到达；用 Lua 脚本
  `if GET < new then SET new EX ttl`，保证 epoch 单调不回退（否则晚到的较小值会让已失效 token
  复活）。iam 直写与 consumer 兜底共用同一 `set_perm_epoch_if_greater`。
- 幂等：重复投递 → set-if-greater 天然幂等，无需 event_id 去重。
- 失败：consumer handle 遇 Redis 错误 warn + 返回 Ok（best-effort；不 wedge 队列）。

### 4.4 接线

gateway `main.rs` spawn 该 consumer（传 redis 连接 clone + event_bus_url + prefix + ttl），
套 4.3 announcement consumer 的「订阅一次 + 轮询连接健康 + 仅断线重订」模式（避免 ephemeral 队列泄漏）。

## 5. 配置、基础设施、测试、验收

### 5.1 配置

- **iam**：新增 `REDIS_URL`（compose 注入；redis 容器已存在）。perm_epoch TTL 取
  `jwt.access_token_ttl_minutes*60`。key prefix 与 gateway 一致（见下）。
- **gateway**：已有 `redis.url` + `redis.prefix`（blacklist 在用）；新增 `EVENT_BUS_URL`
  （digua_common-event consumer 用）+ ttl 配置（与 iam 一致，或 gateway 自己的 access-token TTL 视图）。
- **key prefix 一致性**：`perm_epoch:` 必须用**同一 prefix** 两端写读。gateway 用
  `cfg.redis.prefix`；iam 需用相同 prefix（新增 iam 配置项 `redis_prefix`，默认与 gateway 一致，
  或约定空 prefix + 固定 `perm_epoch:` 前缀）。**实现时必须核对两端 key 完全一致**（否则失效静默失败）。

### 5.2 基础设施

- `definitions.json` 不改（audit `iam.#` 覆盖；gateway 用 ephemeral 队列运行时声明）。
- compose：iam 注入 `REDIS_URL`；gateway 注入 `EVENT_BUS_URL`（redis 已注入）。

### 5.3 测试

- **单元**：
  - gateway perm_epoch 比对纯判定：`iat < epoch → reject`、`iat >= epoch → pass`、`miss → pass`。
  - set-if-greater 语义：先写大值再写小值 → 保留大值。
- **集成（testcontainers MySQL + Redis）**：
  - iam `assign_permissions` → `iam_outbox_events` 出现 `iam.permission.changed`（user_ids=该角色下用户）
    + Redis `perm_epoch:{uid}` 被写且带 TTL。
  - role 禁用/删除、permission 禁用/删除：user_ids 展开正确、事件 + epoch 写入。
  - 空集（角色下无用户）→ 不 enqueue、不写 epoch。
  - `assign_permissions` 事务性：注入中途失败 → 回滚，无半完成（权限表不变、无 outbox 行）。
- **集成（gateway consumer，testcontainers RabbitMQ + Redis）**：发 `iam.permission.changed` →
  consumer 补写 perm_epoch（set-if-greater）→ 断言 Redis 值 == 事件 occurred_at。
- **回归**：`contracts-gen --check`、`check-db-naming`、digua_common-event + iam-service + api-gateway 测试。

### 5.4 Live 冒烟（人工验收）

登录用户 A 拿 token → admin 改 A 所属角色权限 → A 持旧 token 请求 →
gateway 401「permissions changed」→ A 刷新/重登 → 新权限生效。
另测：停 iam 的 Redis 直写（模拟失败）→ 仅靠 gateway consumer 兜底，A 旧 token 仍最终被拦。

## 6. 成功标准

1. 三类权限变更在 iam 侧同事务展开 user_ids + 发 `iam.permission.changed`（outbox）+ commit 后直写 perm_epoch。
2. gateway `auth_middleware` 比对 `iat < perm_epoch` → 401 强制重认证；miss 放行；Redis 失败 fail-open。
3. gateway consumer 订阅 `iam.permission.changed`，用 set-if-greater 兜底补写 perm_epoch（关闭直写 fail-open 窗口）。
4. `iam.permission.changed` 自动落 `audit_events`（零改动验证）。
5. perm_epoch 带 access-token-TTL 自动过期；set-if-greater 保证单调不回退。
6. `assign_permissions` / delete 路径顺手改为事务性。
7. iam↔gateway 的 perm_epoch key prefix 完全一致（实现核对）。
8. 全部测试 + 命名/契约门禁通过。
