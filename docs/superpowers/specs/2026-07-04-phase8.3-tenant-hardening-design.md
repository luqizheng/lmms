> - D5 `check-tenant-scope.js` 阻断 CI（exit 1），与 `check-db-naming` / `check-spec` 一致。启发式 grep + 豁免注释。
> - D6 `get_claims` 加 `Query<TenantIdQuery>` + 3 条 SQL `AND tenant_id = ?`，与 `internal_users` 同模式。

## 1. 背景与问题

Phase 8.2 完成后，业务表已加 `tenant_id`，查询已改 tenant-scoped，但仍有 4 个安全缺口：

1. **JWT 缺 `tid` 仍被接受**：`Principal::from_jwt_payload`（`libs/jwt-ctx/src/principal.rs:73-76`）对缺失 `tid` fallback `unwrap_or(1)`（default tenant）。旧 token 或篡改 token（删 `tid`）仍可访问任意租户数据 —— 只要猜对 user_id。
2. **`get_claims` 无 tenant 过滤**：`UserService::get_claims`（`user_svc.rs:413`）3 条 SQL 全按 `user_id` 直查，JOIN `iam_roles` / `iam_permissions` 不带 tenant 条件。token-service 刷新 token 时调用此端点，若传错 user_id 会跨租户泄露角色/权限。mesh intentions 鉴权可信但缺防御性深度。
3. **无 platform_admin 跨租户能力**：所有用户都被锁在单一租户。运维 / SaaS 运营方无法跨租户查看数据做支持。`default` tenant admin 虽有全部权限但只能看 default tenant 数据。
4. **无自动化 lint 防漏检**：handler 拿了 `TenantScope` 但 SQL 忘加 `tenant_id` 过滤只能靠 code review 发现。8.1 spec §3.5 已标注"8.3 落 `check-tenant-scope.js`"。

## 2. 目标 / 非目标

### 目标

1. **JWT `tid` 缺失硬拒 401**：`Principal::from_jwt_payload` 返 `MissingTenantId` error；gateway fail-fast 也检查 `tid` 存在。
2. **platform_admin 跨租户能力**：全局 `platform_admin` 角色 → JWT `ct: true` claim → `Principal.cross_tenant: bool` → `TenantScope::CrossTenant` → `and_tenant` no-op。
3. **`TenantScope` 改 enum**：编译期保证 handler 调 `and_tenant` 时自动正确处理 cross_tenant，消灭人因遗漏。
4. **`get_claims` 加 tenant 过滤**：3 条 SQL 加 `AND tenant_id = ?`，token-service 调用时传 `?tenant_id=`。
5. **`check-tenant-scope.js` CI lint**：启发式扫描 handler 拿 `TenantScope` 但 SQL 无 `tenant_id`，exit 1 阻断 push。
6. **e2e 跨租户黑名单**：test-case/83 + 自动化 e2e + testcontainers 集成测试。

### 非目标

- platform_admin 管理界面 / 赋权 UI —— 运维手动 DB 操作
- tenant 计费 / quota / 生命周期 —— 产品形态未定
- 跨租户审计日志（记录 platform_admin 访问了哪租户数据）—— 后续安全增强
- gateway 路由感知的 tenant 检测 —— D1 已决策仅收紧 JWT
- `iam_permissions` / `iam_menus` 加 tenant_id —— 8.1/8.2 已定全局
- 前端 platform_admin 视图 / 租户切换 UI —— 前端独立排期

### 3.2 Principal & JWT 收紧

#### Principal 改动（`libs/jwt-ctx/src/principal.rs`）


`from_jwt_payload` 解析逻辑变化：

```rust
// tid: 旧 unwrap_or(1) → 硬拒
let tenant_id = payload
    .get("tid")
    .and_then(|v| v.as_i64())
    .ok_or(PrincipalError::MissingTenantId)?;  // 新 error variant

    .get("ct")
    .and_then(|v| v.as_bool())
```

`PrincipalError` 加 `MissingTenantId` variant：
```rust

```

**影响范围**：
- `Principal::from_request_parts` 的 `Rejection = StatusCode` 不变（仍 401）
- gateway `JwtClaims`（`services/api-gateway/src/jwt.rs`）已有 `custom: HashMap`，`tid` / `ct` 都在 custom 里透传，无需改 struct
- gateway `auth_middleware` 不需要显式检查 `tid` —— 下游 `Principal` extractor 会拒。但为 fail-fast + 明确报错，gateway 在 `validate()` 后加一道 `tid` 存在性检查，缺 `tid` 直接 401「missing tenant claim」

### 3.3 TenantScope enum + digua_common-db 改造

#### TenantScope 改 enum（`libs/jwt-ctx/src/scope.rs`）

```rust
#[derive(Debug, Clone, Copy)]
pub enum TenantScope {
    Single(i64),
    CrossTenant,
}

impl<S: Send + Sync> FromRequestParts<S> for TenantScope {
    type Rejection = StatusCode;
    async fn from_request_parts(parts: &mut Parts, state: &S) -> Result<Self, Self::Rejection> {
        let p = Principal::from_request_parts(parts, state).await?;
        Ok(if p.cross_tenant {
            TenantScope::CrossTenant
        } else {
            TenantScope::Single(p.tenant_id)
        })
    }
}
```

**衍生方法**（给点查询用）：
```rust
impl TenantScope {
    /// Some(tid) for Single, None for CrossTenant
    pub fn tenant_id(&self) -> Option<i64> {
        match self { Self::Single(t) => Some(*t), Self::CrossTenant => None }
    }
}
```

#### and_tenant 改造（`libs/digua_common-db/src/scope.rs`）

```rust
fn and_tenant(mut self, scope: &TenantScope) -> Self {
    match scope {
        TenantScope::Single(tid) => {
            self.push(" AND tenant_id = ").push_bind(*tid);
            self
        }
        TenantScope::CrossTenant => self,  // no-op
    }
}
```

#### 点查询迁移策略

8.2 的点查询模式是 `sqlx::query("... WHERE id = ? AND tenant_id = ?").bind(id).bind(tid)`。对 cross_tenant，有两条路：

**模式 A（QueryBuilder，推荐）**：列表查询已用，点查询也迁：
```rust
let mut qb = QueryBuilder::new("SELECT ... FROM iam_roles WHERE id = ");
qb.push_bind(id);
qb.and_tenant(&scope);  // CrossTenant 时 no-op
let role = qb.build_query_as::<Role>().fetch_optional(&pool).await?;
```

**模式 B（IFNULL，固定 SQL 保形）**：不想迁 QueryBuilder 的点查询：
```rust
// tenant_id = IFNULL(?, tenant_id)
sqlx::query("SELECT ... WHERE id = ? AND tenant_id = IFNULL(?, tenant_id)")
    .bind(id)
    .bind(scope.tenant_id())  // None → IFNULL(NULL, tenant_id) = tenant_id → always true
```

**实施原则**：本期点查询统一走模式 A（QueryBuilder），与 8.2 列表查询风格一致。模式 B 仅在 QueryBuilder 不便时（如 `sqlx::query_as!` 编译期校验宏）作为兜底（当前项目全用 `sqlx::query_as` 运行时，不触发兜底）。8.2 已大量用 QueryBuilder，剩余点查询改造量：iam ~14 处（role_svc 4 / org_svc 6 / user_svc 4）、ntf ~2 处、cfg ~3 处、file ~2 处，共约 21 处。

#### INSERT 不变

INSERT 永远 bind 具体租户 id（`principal.tenant_id`），`cross_tenant` 不影响 INSERT —— platform_admin 建资源时仍须指定归属租户。handler 从 `Principal.tenant_id` 取值（platform_admin 的 `tenant_id` 是其所属租户，通常 default=1）。

#### 破坏性影响

改 `TenantScope` 从 tuple struct → enum，4 处受影响：
- `libs/jwt-ctx/src/scope.rs` — extractor 本体（改）
- `libs/jwt-ctx/tests/scope_test.rs:27` — `assert_eq!(scope.0, 42)` → `assert_eq!(scope, TenantScope::Single(42))`
- `libs/digua_common-db/src/scope.rs:17` — `scope.0` → match
- `libs/digua_common-db/tests/scope_test.rs:12` — `TenantScope(42)` → `TenantScope::Single(42)`

零业务代码破坏（业务代码只通过 `and_tenant` 间接用 `TenantScope`）。

### 3.4 platform_admin 角色 + get_claims 收紧

#### platform_admin 全局角色（V005 迁移）

`iam_roles` 在 8.2 已加 `tenant_id` 列。`platform_admin` 是**全局角色**（`tenant_id=1` default tenant），与 `tenant_admin` 同级但语义不同：

```sql
-- V005__platform_admin_role.sql (mysql + sqlite)
INSERT INTO iam_roles (id, tenant_id, code, name, data_scope, status, created_at, updated_at)
VALUES ('role-platform-admin-seed', 1, 'platform_admin', '平台管理员', 0, 'enabled', NOW(), NOW())
ON DUPLICATE KEY UPDATE id = id;

-- 绑全部全局权限（与 tenant_admin seed 同模式）
INSERT IGNORE INTO iam_role_permissions (role_id, permission_id)
SELECT 'role-platform-admin-seed', id FROM iam_permissions
WHERE status = 'enabled' AND deleted_at IS NULL;
```

**不开放自助注册 platform_admin** —— 仅通过 DB seed / 运维手动赋权。给 default tenant 的 admin 用户绑 platform_admin 角色：
```sql
INSERT IGNORE INTO iam_user_roles (user_id, role_id)
SELECT u.id, 'role-platform-admin-seed' FROM iam_users u
WHERE u.tenant_id = 1 AND u.username = 'admin';
```

**注意**：default tenant 的 admin 同时拥有 `tenant_admin`（8.2 seed）和 `platform_admin`，登录时 `roles` 数组含两者，`cross_tenant = true`。

#### get_claims 加 tenant 过滤（`user_svc.rs:413`）

当前 3 条 SQL 全按 `user_id` 直查无 tenant 过滤。改造为 `TenantIdQuery` 模式（与 `internal_users.rs:16` 对称）：

**路由**（`routes/users.rs:156`）：
```rust
pub async fn get_user_claims(
    State(state): State<AppState>,
    Path(user_id): Path<String>,
    Query(tq): Query<TenantIdQuery>,  // 新增
) -> Result<Json<UserClaimsResponse>, ...>
```

`TenantIdQuery` 复用 `routes/internal_users.rs:16` 已有 struct —— 在 `routes/mod.rs` 加 `pub use internal_users::TenantIdQuery;` 使 `users.rs` 可 import（零结构变动）。

**service**（`user_svc.rs:413`）—— 3 条 SQL 全加 `AND tenant_id = ?`：

```rust
pub async fn get_claims(&self, user_id: &str, tenant_id: i64) -> Result<UserClaimsResponse, IamError> {
    let user = sqlx::query_as(
        "SELECT id, username, email, phone, nickname FROM iam_users \
         WHERE id = ? AND tenant_id = ? AND deleted_at IS NULL AND status = 'active'"
    )
    .bind(user_id).bind(tenant_id)
    .fetch_optional(&self.state.db).await?;

    let roles = sqlx::query_scalar(
        "SELECT r.code FROM iam_roles r \
         JOIN iam_user_roles ur ON r.id = ur.role_id \
         JOIN iam_users u ON u.id = ur.user_id \
         WHERE ur.user_id = ? AND u.tenant_id = ? AND r.deleted_at IS NULL"
    )
    .bind(user_id).bind(tenant_id)
    .fetch_all(&self.state.db).await?;

    let permissions = sqlx::query_scalar(
        "SELECT p.code FROM iam_permissions p \
         JOIN iam_role_permissions rp ON p.id = rp.permission_id \
         JOIN iam_user_roles ur ON rp.role_id = ur.role_id \
         JOIN iam_users u ON u.id = ur.user_id \
         WHERE ur.user_id = ? AND u.tenant_id = ? AND p.deleted_at IS NULL"
    )
    .bind(user_id).bind(tenant_id)
    .fetch_all(&self.state.db).await?;
    // ...
}
```

**调用方改造**（token-service 2 处 HTTP 调用）：
- `routes/refresh.rs:105` 和 `routes/access.rs:72`
- 从旧 token 的 `tid` claim 提取 tenant_id，拼到 URL：`/internal/users/{id}/claims?tenant_id={tid}`

**防御性深度**：mesh intentions 已鉴权可信，但若 service 调用方传错 user_id 仍会跨租户泄露。加 tenant 过滤后，即使传错 user_id 也只查指定租户，不泄露他租户角色/权限。

#### get_claims 与 cross_tenant

token-service 调 get_claims 时**始终传具体 tenant_id**（从旧 token 的 `tid`），不走 cross_tenant。理由：token 签发场景下 tenant 归属是确定的（用户所在租户），platform_admin 刷新 token 时也只取自己租户的 claims。

### 3.5 check-tenant-scope.js lint 工具

#### 检测逻辑

启发式 grep（与 `check-db-naming.js` 同风格），扫 `services/*/src/**/*.rs`：

1. **找 handler 函数**：函数签名含 `TenantScope` 参数（含 `scope: TenantScope`、`_scope: TenantScope`）
2. **检查函数体内是否有 tenant 过滤**：满足以下任一即可通过：
   - 出现 `and_tenant` 调用
   - 出现 `tenant_id` 字符串（SQL 里 `AND tenant_id = ?` 或 bind `.bind(scope.tenant_id())` / `.bind(principal.tenant_id)`）
   - 出现 `TenantScope::CrossTenant` 显式 match（platform_admin handler 特意不过滤）
3. **都不满足 → 报错**：`exit 1` + 文件名:行号 + "handler takes TenantScope but SQL has no tenant_id filter"

#### 误报处理

**已知误报场景**：
- handler 拿 `TenantScope` 但只做 INSERT（INSERT bind `principal.tenant_id`，不调 `and_tenant`）→ 已被规则 2 覆盖（`tenant_id` 字符串出现）
- handler 拿 `TenantScope` 但委托给 service 层函数（SQL 不在 handler 函数体内）→ **报误报**，用 `// tenant-scope: delegated to service` 注释豁免

**豁免机制**：函数上方加 `// check-tenant-scope: delegated` 注释，lint 跳过该函数。与 `check-db-naming.js` 的 `SKIP_IN_SOURCE` 同思路。

#### 实现要点

```javascript
// 伪代码
const HANDLER_PATTERN = /(?:pub\s+)?async\s+fn\s+\w+\s*\([^)]*TenantScope[^)]*\)/g;
const HAS_FILTER = /and_tenant|tenant_id|TenantScope::CrossTenant/;
const EXEMPT = /check-tenant-scope:\s*delegated/;

for (const file of rustFiles) {
  const functions = extractFunctions(code);  // 按 fn 块切分
  for (const fn of functions) {
    if (EXEMPT.test(fn)) continue;
    if (/TenantScope/.test(fn.signature) && !HAS_FILTER.test(fn.body)) {
      error(file, fn.line, "handler takes TenantScope but SQL has no tenant_id filter");
    }
  }
}
```

**函数切分**：用花括号计数（rust 的 `{}` 配对），不依赖 syn/AST —— 与项目现有 lint 脚本风格一致（`check-db-naming.js` 也是 regex）。

#### CI 接入

加入 `package.json` scripts + GitLab CI `test` 阶段 + pre-commit hook：

```json
"check:tenant-scope": "node scripts/check-tenant-scope.js"
```

pre-commit hook（`.pre-commit-config.yaml` / `scripts/git-hooks/pre-commit`）追加一行。

**触发范围**：`services/*/src/**/*.rs` 改动时跑（与 `check-db-naming` 同 trigger）。

#### 不保证 100%

启发式 grep 的固有限制：
- 动态拼接的 SQL（`format!` 拼表名）可能漏检
- service 层委托的 handler 靠豁免注释，注释可能滥用

**核心防线仍是 code review**，lint 是第二道网，拦"明显忘了"的情况。
