# 03. 第一次跑通

> 读完这一章你会知道：从 clone 仓库到看到一个接口正常返回，需要几步、每步在做什么。
>
> 预计耗时：**30 分钟**（首次编译 Rust 会花 5–15 分钟，是正常的）。

---

## 3.1 Clone 仓库

```bash
git clone <你的仓库地址> coder-micro-services
cd coder-micro-services
```

> 💡 仓库地址请咨询你的导师或运维，通常是 GitLab 内网地址。

---

## 3.2 安装工作区依赖

```bash
pnpm install
```

这一步会：
- 安装根目录 `package.json` 里的脚本依赖
- 安装 `tests/e2e/` 里的测试依赖
- 安装 `frontend/` 里的前端依赖（因为前端也是 workspace 成员）

---

## 3.4 启动基础设施

```bash
docker compose -f infrastructure/docker-compose.yml up -d
```

`infrastructure/docker-compose.yml` 现在是 **include 入口文件**，通过 `include:` 自动拉取：
- `docker-compose-infra.yml` — 基础设施 3 件套
- `docker-compose-services.yml` — 7 个业务服务

> 💡 这是 2026-06 的重构结果。对调用方完全透明：所有命令仍用 `-f infrastructure/docker-compose.yml`，无需关心拆分细节。

**启动顺序**（由各 service 的 `depends_on: condition: service_healthy` 自动编排）：

```
mysql + redis + consul          (healthcheck)
        ↓
token-service                   (等 mysql/redis healthy)
        ↓
api-gateway                     (等 consul/redis/token-service healthy)
        ↓
frontend                        (等 api-gateway)

iam-service / notification-service / audit-service / prue_backend
   → 各自等 mysql/redis/consul healthy，与 token-service 并行启动
```

一条 `up -d` 即可，无需手工分步。

**只想启基础设施**（自己 `cargo run` 业务服务时常用）：

```bash
docker compose -f infrastructure/docker-compose.yml up -d mysql redis consul
```

**可观测性**（已 include 进主 compose；如果第一步用的 `docker-compose-infra.yml` 起步，这里单独拉起 overlay）：

```bash
docker compose -f infrastructure/docker-compose-observability.yml up -d
```

overlay 包含：Prometheus（:9090）/ Grafana（:3001）/ Jaeger（:16686）/ OTel Collector / consul-template，挂在主栈的 `superpowers` 网络上。

**验证启动成功**：

```bash
docker ps
# 期望看到 10 个容器均为 Up（含 observability 则 15 个），名称以 infrastructure- 前缀

# Consul UI
open http://localhost:8500
```

> 刚启动时可能还没有服务注册进去，因为 Rust 服务的健康注册需要等 healthcheck 通过（约 10–30s）。

## 3.5 启动第一个后端服务（iam-service）

```bash
cd services/iam-service
cargo run
```

> ⚠️ **首次编译需要 5–15 分钟**，这是正常的。Rust 第一次编译会把所有依赖都编译一遍，后续改代码后增量编译通常只需几秒到几十秒。

如果一切正常，你会看到类似输出：

```
Compiling iam-service v0.1.0 (coder-micro-services/services/iam-service)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 5m 42s
     Running `target/debug/iam-service`
 INFO iam_service: Starting server on 0.0.0.0:8080
 INFO iam_service: Consul registered: iam-service -> 127.0.0.1:8080
```

验证服务已注册到 Consul：回到 http://localhost:8500，搜索 `iam-service`，应看到一条健康的服务记录。

## 3.6 打开 Swagger UI 试调一个接口

在另一个终端（不要关 `cargo run` 的终端），确认 Swagger 已启用：

```bash
curl http://localhost:9081/swagger-ui
# 期望返回 HTML 页面（表示 Swagger UI 正常）
```

浏览器打开：

```
http://localhost:9081/swagger-ui
```

> 为什么端口是 9081 而不是 8081？因为 `iam-service` compose 端口映射是 `9081:8081`——宿主机通过 Docker Compose 把 host 端 `9081` 映射到容器的 `8081`。直接访问 `localhost:8081` 不会冲突（容器内端口），但通常用 host 端口更便于宿主机浏览器 / curl 调试。完整端口表见 [`docs-site/user-manual/11-reference.md` §11.5](../user-manual/11-reference.md#115-服务端口速查phase-5-a-2-之后)。

在 Swagger UI 上：
1. 找到 `POST /iam/auth/login`
2. 点 "Try it out"
3. 填入 body（用户名和密码请咨询你的导师或看数据库初始数据）
4. 点 Execute，看响应

> 💡 如果数据库是全新的（还没有任何账号），登录会失败——先做下一节「3.7 首次初始化管理员」，再回来登录。

## 3.7 首次初始化管理员（空库必做）

全新部署时 `iam_users` 表是空的，**还没有任何账号能登录**。系统为此提供了一个一次性的初始化入口：

```bash
curl -X POST http://localhost:9081/iam/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "username": "admin",
    "password": "至少8位的强密码",
    "nickname": "系统管理员"
  }'
```

返回 `201` 即成功。这个接口的行为要点：

- **只在全系统零用户时开放一次**：只要已存在任何一个用户，再调用就返回 `403 registration closed`。
- **落在默认租户**：首个用户归属数据库迁移预置的默认租户（`id=1`，slug `default`），无需也无法选择租户。
- **自动成为管理员**：系统会为首个用户自动创建 `tenant_admin`（租户管理员）角色并绑定当前全部已启用权限，注册完即可直接登录。注意它是**默认租户的管理员**，不是跨租户超级管理员（`platform_admin`）。
- 前端可用 `GET /iam/auth/setup-status` 判断是否需要展示初始化向导页，详见 [前端登录态刷新机制 §1.3](../guides/frontend-auth.md)。

> ⚠️ **安全提醒**：该接口无鉴权、先到先得。私有化部署交付后请**第一时间**完成初始化，否则任何能访问这个接口的人都能抢走首个管理员账号。

> 💡 想再创建**更多租户**？用 `POST /iam/tenants`（随时可用）：它会新建一个租户，并让请求体里的 `admin_username` 成为**那个新租户**的管理员。两条注册路径不要混淆，详见 [ADR-003 多租户架构](../decisions/ADR-003-multi-tenancy-architecture.md)。

## 3.8 启动前端

在**新的终端**（不要关后端的终端）：

```bash
pnpm --filter @coder/frontend run dev
```

> 前端默认端口 **8848**，浏览器打开：http://localhost:8848

> 💡 前端的 Vite 代理已将 `/api` 路径转发到 `http://127.0.0.1:3000`（api-gateway），所以前端接口请求会**自动**经过网关。代理配置在 `frontend/vite.config.ts:18-24`。

如果你现在打开前端页面并尝试登录，请求路径会是：

```
浏览器 → localhost:8848 (前端) → /api/iam/auth/login → api-gateway:3000 → iam-service:8080
```

## 3.9 关闭与清理

```bash
# 关前端：按 Ctrl+C（在 dev 终端里）

# 关后端：按 Ctrl+C（在 cargo run 终端里）

# 关基础设施（如果起了 observability，要先关 overlay 再关主栈）
docker compose -f infrastructure/docker-compose-observability.yml down
docker compose -f infrastructure/docker-compose.yml down

# ⚠️ 加上 -v 会清除数据卷（MySQL 里的数据会被清空）
docker compose -f infrastructure/docker-compose.yml down -v
```

> 💡 日常开发建议只用 `down`（保留数据），重启时数据还在。只有想完全重置数据库时才用 `down -v`。
