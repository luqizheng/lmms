## 5.1 连接本地数据库

### 连接命令

```bash
# 用 mysql CLI（需先安装 MySQL client）
mysql -h 127.0.0.1 -P 3306 -u root -prootpass

# 或进入 Docker 容器里执行

docker exec -it coder-micro-services-mysql-1 mysql -uroot -prootpass
```

进入后可以看到各服务的数据库：

```sql
SHOW DATABASES;
-- 期望看到：superpowers（或各服务自己的库）

USE superpowers;
SHOW TABLES;
```

### GUI 工具（推荐 DBeaver / DataGrip / TablePlus）

| 配置项 | 值 |
|--------|-----|
| 主机 | `127.0.0.1` |
| 端口 | `3306` |
| 用户 | `root` |
| 密码 | `rootpass` |
| SSL | 关闭 |

> ⚠️ 不要连 Docker 容器名 `mysql`，那是容器间通信用的地址。宿主机上连 `127.0.0.1`。

## 5.2 为什么一份迁移要写两遍

本项目同时支持 **MySQL** 和 **SQLite** 两种方言：

| 场景 | 数据库 | 原因 |
|------|--------|------|
| **生产环境** | MySQL | 事务、外键、性能 |
| **本地轻量测试** | SQLite | `prue_backend` 默认用 SQLite，免起 MySQL |

所以每个迁移都存两份：

```
services/iam-service/migrations/
├── mysql/
│   └── 20240101000000_init.sql
└── sqlite/
    └── 20240101000000_init.sql
```

---

## 5.3 迁移文件命名

```
YYYYMMDDHHMMSS_<描述>.sql
```

例如：`20240101000000_init.sql`

- 前 14 位是时间戳，**必须严格递增**
- 后面的描述用下划线连接英文单词

不需要手动写 SQL，项目内置了 AI Skill `coder-migrate-db`：

1. 在项目根目录运行：
   ```bash
   # 该 skill 会自动生成 MySQL + SQLite 双版本的迁移文件
   ```

2. 生成的文件会放在 `services/<svc>/migrations/mysql/` 和 `services/<svc>/migrations/sqlite/`

3. 自动执行迁移（启动服务时会自动跑）

> 详细用法请参考：`.agents/skills/coder-migrate-db/SKILL.md`

### ⚠️ 用户引用字段统一 `VARCHAR(64)`

**凡是引用用户身份的列**（`user_id` / `created_by` / `updated_by` / `operator_id` / `actor_id` / `owner_id`），新表 / 新列**必须用 `VARCHAR(64)`**（SQLite 用 `TEXT`）——本平台 user id 是随机字符串（UUID / Nano ID），**不是自增整数**。

- ❌ `created_by BIGINT NOT NULL` —— JWT `sub` 是随机字符串，根本写不进去；
- ✅ `created_by VARCHAR(64) NOT NULL`；
- 现存历史表长度不一（`VARCHAR(32/36/64/128)`），**不动旧表**，新表一律 64。

权威定义：[`contracts/db-conventions.md`](../../contracts/db-conventions.md) §「用户引用字段类型约定」。

## 5.5 sqlx 离线模式

SQLx 的核心特性：**编译期检查 SQL 语句**。

这意味着：
- 写 `sqlx::query!("SELECT * FROM users WHERE id = ?", id)` 时
- 编译器会**实际连到数据库**去检查这条 SQL 的语法和返回字段类型
- 如果表不存在、字段名写错、类型不匹配 —— **编译就报错**，不用等到运行时

### 什么时候需要 `cargo sqlx prepare`

如果你改了数据库 schema（加表、加字段、改类型），sqlx 缓存的数据库元数据就过期了，需要重生成：

```bash
# 1. 确保数据库已启动且迁移已执行
docker compose -f infrastructure/docker-compose.yml up -d

# 2. 进入服务目录
cd services/iam-service

# 3. 重新生成 sqlx 离线数据
cargo sqlx prepare
```

这会在 `services/<svc>/` 目录下生成/更新 `sqlx-data.json` 文件。

### CI 为什么会失败

CI 环境不连真实数据库，而是读取 `sqlx-data.json` 做编译期检查。如果：
- 你改了 SQL 但没跑 `cargo sqlx prepare`
- 或者 `sqlx-data.json` 没提交到 git

CI 就会报类似：

```
error: error returned from database: (code: 1) no such table: xxx
```

> 💡 **黄金法则**：改 SQL → `cargo sqlx prepare` → 提交 `sqlx-data.json` → push
