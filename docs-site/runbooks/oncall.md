## 4. 什么算紧急情况

### 4.1 必须立即处理的

| 场景 | 例子 | 响应时间 |
|------|------|----------|
| 服务完全不可用 | 所有接口返回 5xx | 5 分钟 |
| 数据泄露风险 | 数据库可公开访问 | 立即 |
| 认证系统故障 | 所有人无法登录 | 5 分钟 |
| 支付/订单相关 | 交易无法完成 | 5 分钟 |

### 4.2 应该处理的（但不紧急）

| 场景 | 例子 | 响应时间 |
|------|------|----------|
| 部分接口慢 | 个别查询 > 5s | 30 分钟 |
| 非关键服务异常 | 通知服务偶尔失败 | 2 小时 |
| 监控告警 | 错误率上升但 < 5% | 1 小时 |

### 4.3 不算紧急的

- 需求/功能咨询
- 非生产环境问题
- 文档更新
- 性能优化（除非严重影响用户体验）

## 5. 事件分级

### 5.1 分级标准

| 级别 | 定义 | 通知范围 | 响应/恢复目标 |
|------|------|----------|---------------|
| SEV1 | 核心服务完全不可用 | 全员 + CTO | 15 分钟 / 1 小时 |
| SEV2 | 核心服务部分不可用 | 团队 + EM | 30 分钟 / 4 小时 |
| SEV3 | 非核心服务异常 | On-call | 2 小时 / 8 小时 |
| SEV4 | 潜在风险 / 监控告警 | On-call | 24 小时 |

### 5.2 分级决策树

```
服务是否完全不可用？
├── 是 → SEV1 或 SEV2（是否核心服务？）
└── 否 → 是否有数据泄露风险？
         ├── 是 → SEV1
         └── 否 → 影响多少用户？
                  ├── > 50% → SEV2
                  ├── 10-50% → SEV3
                  └── < 10% → SEV4
```

## 6. 事件响应流程

### 6.1 发现阶段

```bash
# 1. 确认问题存在
curl -i http://localhost:3000/health

# 2. 查看监控告警
# [Prometheus/Grafana 链接]

# 3. 创建事件记录
# 在 #incidents-YYYY-MM-DD 频道记录事件
```

### 6.2 止血阶段

```bash
# 1. 快速止血优先
# - 重启异常服务
docker compose -f infrastructure/docker-compose-services.yml restart <svc>

# - 回滚到上一版本（如果刚部署）
git checkout <previous-sha>
docker compose -f infrastructure/docker-compose-services.yml up -d

# - 启用备用服务（如果有）

# 2. 通知相关方
Slack: @here [UPDATE] <止血措施>
```

### 6.3 诊断阶段

```bash
# 1. 收集信息
# - 服务日志
docker logs -f <svc> --tail 200

# - 链路追踪
# 查看 Jaeger: http://localhost:16686

# - 指标
# 查看 Grafana: http://localhost:3001

# 2. 确认影响范围
# - 多少用户受影响
# - 哪些服务受影响
# - 是否有数据损失
```

### 6.4 解决阶段

```bash
# 1. 执行修复
# 2. 验证修复
curl http://localhost:3000/health
pnpm -C tests/e2e test:smoke

# 3. 通知解决
Slack: @here [RESOLVED] <问题> - 原因: <简述> - 解决时间: <时长>
```
